# Флоу ограничений и спецификаций: что проверяется, как и зачем

Документ описывает, как в проекте устроена цепочка **спецификация → генерация →
реализация → проверка**, какие ограничения стоят на каждом шаге, каким механизмом
они срабатывают и какую именно ошибку каждое из них предотвращает. Это карта
«почему нельзя просто написать код»: каждое ограничение здесь привязано к
конкретному сценарию, который оно закрывает.

Если коротко: правда живёт в контрактах, код из контрактов генерируется, поведение
задаётся тестом до реализации, а всё, о чём договорились, проверяет машина, а не
ревью. Договорённость, которую нельзя проверить автоматически, держится процедурой
(скиллы) и явно помечена в разделе «Что не проверяется автоматически».

## 1. Точки спецификации

В репозитории четыре точки спецификации. Три задают **форму**, четвёртая —
**поведение**. Плюс два документа, которые фиксируют не «что», а «почему» и
«что предстоит снести».

| Спецификация | Файл-источник | Что задаёт | Генерат | Кто потребляет генерат | Чем защищена |
|---|---|---|---|---|---|
| HTTP-контракт | `docs/api/openapi.yaml` | пути, поля, типы, обязательность, границы, enum, коды ответов | `gen/api/generated.go` (strict-server, embedded spec), `front/src/gen/api.d.ts` | `internal/httptransport`, `front/src/api/client.ts` | `protect-gen.sh`, `generate-check`, `OapiRequestValidator` в рантайме, `test-guard` |
| Схема данных | `internal/db/migrations/*.sql` + `internal/db/queries/*.sql` | DDL и типизированные запросы | `gen/db` (sqlc, pgx/v5) | `internal/repository` | `protect-gen.sh` (миграции forward-only), sqlc сверяет запросы с DDL, `generate-check`, `guard` (SQL вне репозитория) |
| Дизайн | `DESIGN.md` (формат google-labs design.md) | токены: цвета, типографика, радиусы, отступы, компоненты | `front/src/gen/theme.css` (`@theme` Tailwind v4) | `front/src/design-system/`, компоненты | `design-lint`, `protect-gen.sh`, `generate-check`, `design-guard` |
| Поведение | `*_test.go` в транспорте и usecase | что происходит при конфликте, лимит по умолчанию, что считается пустым именем | — (моки `gen/mocks` по `ports` и `contracts.go`) | реализация домена и транспорта | `test-guard`, `make red`, `make test` |
| «Почему» | `docs/adr/NNNN-*.md` | контекст, альтернативы, причина выбора | — | читатель кода через маркер `// ADR:` | только процедура |
| «Что снести» | `docs/adr/DEPRECATIONS.md` | очередь отложенных удалений с проверяемым условием | — | маркер `// DEPRECATED:` | только процедура |

Ключевое свойство: **источник правится руками, генерат — никогда**. Контракт и
порождённый им генерат коммитятся вместе. Обратный порядок («сначала код, потом
контракт») ломается сам: следующая генерация затирает написанное.

## 2. Сквозной флоу и ограничения на каждом шаге

Любое контрактное изменение проходит один и тот же путь. На каждом шаге указано,
какое ограничение сработает, если шаг пропустить или сделать не так.

| Шаг | Что делается | Что сработает при нарушении |
|---|---|---|
| 1. Контракт | правится `openapi.yaml`, миграция + `*.sql`, `DESIGN.md` | правка `gen/` или закоммиченной миграции блокируется хуком `protect-gen.sh` |
| 2. Генерация | `make generate` | `generate-check` валит `verify`, если генерат не совпал с контрактом |
| 3. Заглушка | сигнатуры объявляются с `errors.New("не реализовано")`, чтобы код собирался | `make red` отказывает, если красный получен от компилятора, а не от ассерта |
| 4. Тест | кейс на каждый исход, ожидание из контракта литералом | `test-guard`: код ответа из спеки без кейса, usecase без теста; `make red`: тест зелёный до реализации |
| 5. Реализация | правило в `entity`, сценарий в `usecase`, данные в `repository`, маппинг в `httptransport/schemas` | `depguard` (границы слоёв), `guard` (env, SQL, `panic`, `context.TODO()`) |
| 6. Диверсия | реализация намеренно ломается, должен упасть именно этот кейс | не проверяется автоматически, см. раздел 5 |
| 7. ADR | нетривиальное решение фиксируется в `docs/adr/` | не проверяется автоматически |
| 8. Готово | `make verify` зелёный, генерат закоммичен вместе с контрактом | `verify` — единственный признак «готово»; коммитит человек, агенту `git commit` запрещён |

Для UI тот же путь: `DESIGN.md` → `make generate` → компонент со story на моковых
данных → визуальная проверка скриншотом → подключение к API через типизированный
клиент. Ограничения: `design-lint`, `design-guard`, `protect-gen.sh` на `theme.css`.

## 3. Три уровня срабатывания

Ограничения делятся по моменту, когда они срабатывают. Чем раньше уровень, тем
дешевле ошибка.

1. **Превентивные, в момент действия агента.** PreToolUse-хук и permissions в
   `.claude/settings.json`. Запрещённое действие не выполняется вовсе.
2. **Статические, в `make verify`.** Скрипты и линтеры, не требующие БД, докера и сети.
   Запускаются локально и в CI, это и есть definition of done.
3. **Рантайм.** Валидация запросов против спеки в HTTP-сервере, проверка запросов
   sqlc против DDL при генерации. Работают уже в собранном сервисе или при генерации.

Договорённости, для которых нет механизма ни на одном из уровней, вынесены в раздел 5.

## 4. Ограничения по одному

Для каждого: что проверяет, как именно, зачем, что делать при срабатывании,
чего не ловит.

### 4.1. Хук `protect-gen.sh` — генерат и миграции неизменяемы

- **Где:** `.claude/hooks/protect-gen.sh`, подключён в `.claude/settings.json` как
  PreToolUse на `Edit|Write|MultiEdit|NotebookEdit|Bash`.
- **Что проверяет.** Две вещи. Первая: цель записи лежит в каталоге `gen/` на любом
  уровне вложенности (регэксп `(^|/)gen/`), то есть и `gen/`, и `front/src/gen/`.
  Вторая: цель записи — файл в `db/migrations/`, который уже под контролем версий
  (`git ls-files --error-unmatch`).
- **Как именно.** Для Edit/Write берётся `file_path`. Для Bash команда режется по
  `;`, `&&`, `||`, `|` и переводу строки, каждый сегмент разбирается `shlex`, и
  целями записи считаются только: правый операнд `>`/`>>`, аргументы `sed -i`,
  последний аргумент `mv`/`cp`/`install`, аргументы `rm`/`truncate`/`shred`/`unlink`,
  `tee`, `dd of=`, `perl`/`python -i`. Упоминание пути в heredoc, в аргументе `grep`
  или в тексте коммита целью записи не считается, поэтому чтение и поиск по `gen/`
  не блокируются.
- **Зачем.** Правка генерата теряется при следующем `make generate`, и правка
  выглядит сделанной ровно до первой регенерации. Правка накаченной миграции
  разъезжается с состоянием прода: у прода уже применена старая версия файла,
  а `golang-migrate` её повторно не выполнит.
- **При срабатывании.** Правится источник: `openapi.yaml`, `*.sql`, интерфейсы в
  `ports`/`contracts.go`, `DESIGN.md`. Для схемы — новая пара через
  `make migrate-create name=...`.
- **Fail-closed.** Без `python3` или при неразобранном JSON хук не пропускает, а
  блокирует с кодом 2. Гардрейл, который тихо отключился, хуже отсутствующего.
- **Чего не ловит.** Запись через программу, которую хук не знает (например
  собственный скрипт, открывающий файл на запись). Это осознанная граница: хук
  защищает от рутинной ошибки, а не от целенаправленного обхода.

### 4.2. Permissions в `.claude/settings.json`

- **Что запрещено:** `Read(.env*)`, `Read(**/.env*)`, `Bash(git push:*)`,
  `Bash(git commit:*)`, `Bash(rm -rf:*)`.
- **Зачем.** `.env` содержит секреты; агент не должен их даже читать, чтобы они не
  попали в контекст и логи. Коммит и пуш остаются за человеком: это точка, где
  человек подтверждает, что `make verify` зелёный и генерат закоммичен вместе с
  контрактом. `rm -rf` закрыт как необратимое действие.
- **Следствие для процесса.** Порядок «тест до кода» нельзя проверить по истории
  git, потому что историю пишет человек. Поэтому автоматика проверяет наличие
  спецификации и осмысленность красного, а порядок держится процедурой
  (ADR-0008).

### 4.3. `make generate-check` — генерат совпадает с контрактом

- **Как.** Выполняет `make generate` и `design-lint`, затем `git status --porcelain`
  по `gen/` и `front/src/gen/`. Любое отличие — отказ с диффом.
- **Зачем.** Ловит два сценария: контракт изменили, а генерат не перегенерировали;
  генерат подправили руками мимо хука. В обоих случаях код и контракт говорят
  разное, и клиент фронта получает типы, не совпадающие с сервером.
- **При срабатывании.** `make generate` и закоммитить `gen/` и `front/src/gen/`
  вместе с контрактом.
- **Особенность моков.** `generate-mocks` сначала удаляет `gen/mocks` целиком:
  mockery не удаляет моки переименованных или удалённых интерфейсов, и без очистки
  они жили бы в `gen/` вечно, ломая эту же проверку.

### 4.4. `design-lint` — контракт дизайна валиден

- **Как.** `design.md lint ../DESIGN.md` официальным CLI `@google/design.md`.
  Дополнительно `gen-theme.mjs` отказывает, если экспорт не содержит `@theme`.
- **Зачем.** Невалидный `DESIGN.md` дал бы пустую или неполную тему, и компоненты
  молча потеряли бы токены. Проверка на `@theme` закрывает случай, когда CLI
  отработал, но ничего не экспортировал.

### 4.5. `depguard` в `make lint` — границы слоёв

- **Где:** `.golangci.yml`, секция `depguard.rules`. Три правила.
- **`domain`** (`internal/service/**`, кроме тестов): запрещены `gen`, echo, pgx,
  `internal/repository`, `internal/httptransport`, `internal/server`, `internal/app`.
- **`transport`** (`internal/httptransport/**`): запрещены `gen/db` и pgx.
- **`repository`** (`internal/repository/**`): запрещён `gen/api`.
- **Зачем.** Зависимость идёт только внутрь: `cmd → app → usecase → entity`, адаптеры
  знают про домен, домен про адаптеры — нет. Без запрета на `internal/repository`
  usecase начал бы принимать конкретный `*item.Repository` вместо интерфейса из
  своего `contracts.go`, и тест без БД стал бы невозможен. Без запрета `gen/api` в
  репозитории модели HTTP просочились бы в слой данных, и смена формы ответа
  тянула бы за собой миграцию.
- **Почему тесты домена исключены.** Моки лежат в `gen/mocks`, и запрет импорта
  генерата сделал бы невозможным их использование там, где они и нужны.
- **Почему `gen` исключён из линтера целиком.** Генерат не правится, значит и
  замечания к нему бессмысленны.
- **Чего не ловит.** Всё, что не выражается импортом: SQL-строка в хендлере,
  чтение окружения. Для этого есть `guard`.

### 4.6. `make guard` — правила, не выражаемые импортами

Скрипт `scripts/guard.sh`, четыре grep-правила по `internal/` и `cmd/` без тестов.

| Правило | Что ищет | Где разрешено | Зачем |
|---|---|---|---|
| Окружение | `os.Getenv`, `os.LookupEnv` | только `internal/config/` | конфиг читается в одном месте, иначе его нельзя ни проверить, ни задокументировать; у параметра либо дефолт, либо он секрет без дефолта |
| `context.TODO()` | любой вызов | нигде | `TODO` означает «здесь не подумали»; каждый внешний вызов должен получать настоящий контекст с таймаутом |
| SQL | `select`, `insert into`, `update … set`, `delete from` в строках, raw-литералах в бэктиках и в начале строки | только `internal/repository/` | запрос из транспорта или домена ломает слои молча, компилятор его не заметит; поиск по бэктикам закрывает самый частый способ протащить SQL мимо слоя |
| `panic(` | любой вызов | только `internal/app/` | падать нормально только при сборке графа; в рабочем коде фатальная ошибка возвращается из `run()` и завершает процесс ненулевым кодом |

**Чего не ловит.** SQL, собранный конкатенацией, и чтение окружения через
сторонние библиотеки. Это граница дешёвой grep-проверки, а не пробел в
договорённости.

### 4.7. `make test-guard` — спецификация тестами существует

Скрипт `scripts/test-guard.sh`, ADR-0008. Проверяет **наличие**, а не «зелёный ли»,
это делает `make test`.

- **Правило 1: каждый код ответа из спеки имеет кейс в тестах транспорта.** Из
  `openapi.yaml` awk-парсером вынимаются пары `operationId → код`, отступы
  вычисляются от самой операции, а не зашиты числом. Для каждой пары ищется в
  `internal/httptransport/*_test.go` имя вида `<OperationId>_?<код>`
  (`CreateItem_409`, `createItem409`). Сейчас в спеке восемь пар: `getHealth`
  200/503, `listItems` 200/400, `createItem` 201/400/409, `getItem` 200/404.
- **Правило 2: каждая операция домена имеет тест.** Для каждого каталога
  `internal/service/usecase/*/` должен существовать `*_test.go`.
- **Fail-closed.** Если число `operationId` в спеке не совпало с числом разобранных
  операций, скрипт отказывает: переформатированная спека (prettier, yq) не должна
  молча превращать гардрейл в no-op.
- **Зачем.** Форму задаёт спека, поведение задаёт тест. Эндпоинт с кодом ответа,
  на который нет кейса, имеет незаданное поведение: неизвестно, при каких условиях
  этот код возвращается. Операция без теста не имеет спецификации вовсе.
- **Чего не ловит.** Качество ожидания. Кейс, который называется правильно, но
  проверяет не то, пройдёт. Против этого работает `make red` и диверсия.

### 4.8. `make red RUN=<тест>` — красный осмысленный

Скрипт `scripts/red.sh`. Не входит в `verify`, вызывается на шаге red цикла TDD.

- **Как.** Запускает `go test -run <регэксп>` и требует ненулевого кода выхода.
  Затем отказывает, если в выводе есть `build failed`, `setup failed`, `undefined:`,
  `cannot find package`, `no test files`, `no tests to run`.
- **Зачем.** Три ложных красных. Тест зелёный до реализации — он не задаёт нового
  поведения или уже реализован. Тест не запустился — опечатка в имени. Тест упал от
  компилятора — он ещё не дошёл до ассерта и ничего не проверяет. Именно поэтому
  порядок начинается с заглушки сигнатуры: в Go тест на отсутствующую функцию не
  компилируется, и красный получается не тот.
- **Чего не ловит.** Красный от ассерта с неверной причиной. Скрипт напоминает
  сверить причину провала с предсказанной, но сверяет человек.

### 4.9. `make design-guard` — UI только на токенах

- **Как.** grep по `#[0-9a-fA-F]{3,8}` в `*.vue` внутри `front/src/design-system`
  и `front/src/components`.
- **Зачем.** Смена палитры в `DESIGN.md` должна менять весь UI без правки
  компонентов. Один захардкоженный hex делает компонент невидимым для контракта:
  тема поменялась, а он остался прежним.
- **Чего не ловит.** `rgb()`, `hsl()`, именованные цвета CSS, inline-стили в TS.
  Дешёвая проверка на самый частый случай.

### 4.10. Рантайм: `OapiRequestValidator` и обработчик ошибок

- **Где:** `internal/server/httpserver/server.go`.
- **Что делает.** Каждый запрос к `/api` валидируется против встроенной в бинарь
  спеки до вызова хендлера: типы, обязательность, форматы, границы, enum.
  Не-`/api` пути (SPA) валидатор пропускает. Все ошибки API, включая ошибки
  middleware, отдаются в формате спеки через `apiErrorHandler`.
- **Зачем.** Форма запроса описана один раз в `openapi.yaml` и не дублируется в
  коде. Хендлер получает уже корректные данные и проверяет только инварианты
  предметной области. Единый обработчик ошибок нужен, чтобы 500 не утекали с
  текстом SQL, именами таблиц и `err.Error()` драйвера.
- **Сопутствующие ограничения сервера.** `ReadHeaderTimeout` 5s, `ReadTimeout` и
  `WriteTimeout` 30s, `IdleTimeout` 120s: медленный клиент не держит соединение
  бесконечно. CORS только из `CORS_ORIGINS`. Служебный порт с `/livez`, `/readyz`
  и pprof живёт отдельно и в compose не публикуется.

### 4.11. Генерация как проверка: sqlc и strict-server

- **sqlc сверяет запросы с DDL.** В `sqlc.yaml` схемой указан каталог миграций,
  поэтому запрос к несуществующей колонке падает на `make generate`, а не в рантайме.
- **strict-server.** `oapi-codegen` с `strict-server: true` генерирует интерфейс,
  где у каждой операции типизированные запрос и набор ответов по кодам из спеки.
  Хендлер физически не может вернуть код, которого нет в спеке: это ошибка
  компиляции. `embedded-spec: true` даёт валидатору ту же спеку, что и коду.
- **mockery.** Моки генерируются по всем интерфейсам в `ports` и `usecase/**`.
  Изменение интерфейса без регенерации ловит `generate-check`; мок, написанный
  руками, расходится с интерфейсом при первой же правке.

### 4.12. `make migrate-create` — нумерация от максимума

Номер новой миграции берётся от максимального существующего, а не от количества
файлов. Иначе при удалённой или пропущенной миграции счёт по количеству попадал бы
в уже занятый номер и затирал закоммиченную пару.

### 4.13. `make verify` и `make verify-full`

`verify` = `generate-check` + `lint` + `guard` + `test-guard` + `test` + `design-guard`.
Всё без докера и сети, поэтому запускается локально за секунды и в CI без
инфраструктуры. `verify-full` добавляет `test-migrations` (up → down → up на живой
БД): проверяет, что у каждой миграции есть работающий `down`, и нужен перед
изменением схемы.

## 5. Что не проверяется автоматически

Эти договорённости держатся процедурой в скиллах и ревью. Они перечислены явно,
чтобы не создавать иллюзии, будто зелёный `verify` их подтверждает.

| Договорённость | Почему нет автоматики | Чем держится |
|---|---|---|
| Тест написан до реализации | коммитит человек, история git не даёт надёжного сигнала | скиллы `/tdd`, `/add-endpoint`, `/add-usecase`; `make red` как обязательный шаг |
| Диверсия: тест падает при намеренной поломке | мутационное тестирование отвергнуто в гейте как долгое и шумное (ADR-0008) | шаг 6 процедуры; пересмотреть, если появится дешёвый инструмент в CI |
| Ожидание из контракта, а не из кода | тавтологию (`want := limit; if want <= 0 …`) grep не отличит от честного ожидания | ревью; правило «литералом, без констант реализации» |
| ADR на нетривиальное решение | «нетривиальность» машиной не определяется | скилл `/new-adr`, маркер `// ADR:` в коде |
| Expand/contract и запись в `DEPRECATIONS.md` | обратная совместимость проверяется только против прод-клиентов | правило «breaking-изменение только отдельным шагом», маркер `// DEPRECATED:` с проверяемым условием |
| Время наружу в UTC, логи без секретов, горутина с владельцем | нет дешёвого статического признака | принципы бэкенда в `CLAUDE.md`, тестовые фикстуры с не-UTC временем в транспорте |
| Story до подключения к API, визуальная проверка скриншотом | процесс, а не артефакт | скиллы `/add-component`, `/update-design` |
| Поведение без контракта помечено `// CHARACTERIZATION:` | пометка добровольная | ADR-0008 |

## 6. Принцип fail-closed

Все гардрейлы построены на одном правиле: **гардрейл, который молча ничего не
проверил, хуже отсутствующего**, потому что создаёт ложную уверенность. Где это
реализовано:

- `protect-gen.sh` блокирует без `python3` и при неразобранном JSON вместо того,
  чтобы пропустить.
- `test-guard.sh` отказывает, если из спеки разобралось не столько операций,
  сколько объявлено.
- `gen-theme.mjs` отказывает, если экспорт `DESIGN.md` не содержит `@theme`.
- `red.sh` считает красный от компилятора отказом, а не успехом.
- `generate-check` показывает дифф, а не просто код выхода.

При добавлении нового ограничения это правило обязательно: проверка, которая при
неожиданном входе возвращает «всё хорошо», не принимается.

## 7. Куда добавлять новое ограничение

| Что хочется запретить | Куда | Почему туда |
|---|---|---|
| Импорт пакета из слоя | `depguard` в `.golangci.yml` | выражается импортом, проверяется компилятором и линтером точно |
| Паттерн в коде, не выражаемый импортом (вызов, строка) | `scripts/guard.sh` | grep дешёвый и прозрачный; правило и его «зачем» лежат рядом в комментарии |
| Отсутствие артефакта (теста, файла) | `scripts/test-guard.sh` или новый скрипт в `scripts/` | проверка наличия, а не содержания |
| Правка файла, который должен меняться через источник | `.claude/hooks/protect-gen.sh` | срабатывает до действия, а не после |
| Действие агента, которое должен подтверждать человек | `permissions.deny` в `.claude/settings.json` | не выполняется вовсе |
| Форма входных данных API | `openapi.yaml` | проверит валидатор в рантайме и типы на компиляции, в коде не дублируется |
| Инвариант предметной области | конструктор сущности в `entity` | некорректный объект нельзя создать, проверка не дублируется в транспорте |

Новый шаг обязан попасть в `make verify`, если не требует докера и сети, и в
`verify-full`, если требует. Ограничение, которого нет в `verify`, для процесса не
существует.

## 8. Быстрая диагностика срабатываний

| Сообщение | Причина | Что делать |
|---|---|---|
| «Файлы в gen/ и front/src/gen/ генерируются, править их бессмысленно» | попытка правки генерата | править источник, `make generate` |
| «Эта миграция уже под контролем версий» | правка закоммиченной миграции | `make migrate-create name=...`, новая пара |
| «генерат разошёлся с контрактами» | не перегенерировали или правили генерат | `make generate`, закоммитить `gen/` и `front/src/gen/` |
| «домен не зависит от …» (depguard) | импорт против направления зависимостей | объявить интерфейс в `contracts.go` или `ports`, зависимость передать снаружи |
| «чтение окружения вне internal/config» | `os.Getenv` в коде | добавить поле в `config.Config` |
| «SQL вне internal/repository» | запрос в транспорте или домене | вынести в `internal/db/queries/*.sql` и репозиторий |
| «panic вне internal/app» | паника в рабочем коде | вернуть ошибку |
| «код ответа из спеки не покрыт тестом» | нет кейса `<OperationId>_<код>` в тестах транспорта | написать кейс, ожидание из спеки |
| «операция домена без теста» | каталог в `usecase/` без `*_test.go` | тест на каждый исход операции |
| «зелёный до реализации» (`make red`) | тест не задаёт нового поведения или не запустился | проверить имя и ожидание |
| «падение не от ассерта» (`make red`) | код не собирается | сначала заглушка сигнатуры |
| «хардкод hex в компоненте» | сырой цвет в `.vue` | токен-утилита из `theme.css`, при необходимости новый токен в `DESIGN.md` |
| «design.md export не вернул @theme» | невалидный `DESIGN.md` | `make design-lint`, исправить контракт |
