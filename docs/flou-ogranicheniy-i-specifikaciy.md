# Флоу ограничений и спецификаций: что проверяется, как и зачем

Документ описывает, какие ограничения стоят на пути от задачи до «готово», каким
механизмом они срабатывают и какую ошибку каждое предотвращает.

Если коротко: что делаем — задаёт план этапа, как ведёт себя Chrome — спайк на
реальном браузере, как ведёт себя CLI — тест, написанный до кода, а всё, о чём
договорились, проверяет машина. Договорённость без автоматики держится процедурой
(скиллы) и явно перечислена в разделе 5.

## 1. Точки спецификации

| Спецификация | Где | Что задаёт | Чем защищена |
|---|---|---|---|
| Этап | `docs/plans/etap-*.md` + реестр | объём, команды, наблюдаемый критерий готовности | только процедура (`/new-plan`) |
| Поведение Chrome | спайк этапа → раздел «Результаты спайка» в ADR | что CDP действительно делает: повтор консоли, стабильность `backendNodeId`, сброс эмуляции | только процедура |
| Поведение CLI | `*_test.go`, e2e в `internal/e2e/` | коды выхода, stdout/stderr, побочные эффекты | `make red`, `make test`, `make test-e2e`, `TestEveryCommandHasE2ECase` (команда без кейса) |
| «Почему» | `docs/adr/NNNN-*.md` | контекст, альтернативы, причина выбора | только процедура, маркер `// ADR:` |
| «Что снести» | `docs/adr/DEPRECATIONS.md` | очередь отложенных удалений с проверяемым условием | только процедура, маркер `// DEPRECATED:` |

## 2. Сквозной флоу

| Шаг | Что делается | Что сработает при нарушении |
|---|---|---|
| 1. План | этап в реестре, критерий готовности | — |
| 2. Спайк | допущение о Chrome проверяется на реальном браузере | — (см. раздел 5) |
| 3. Заглушка | сигнатура с `errors.New("не реализовано")` | `make red` отказывает при красном от компилятора |
| 4. Тест | кейс на каждый исход, ожидание из плана литералом | `make red`: тест зелёный до реализации или не запустился |
| 5. Реализация | `internal/<пакет>`, команда в `cmd/chromectl` | `depguard`, `guard` |
| 6. Диверсия | реализация намеренно ломается | не проверяется автоматически |
| 7. ADR | нетривиальное решение | не проверяется автоматически |
| 8. Готово | `make verify` зелёный | `verify` — единственный признак «готово»; коммитит человек |

## 3. Уровни срабатывания

1. **Превентивные, в момент действия агента.** Permissions в `.claude/settings.json`.
2. **Статические, в `make verify-unit`.** Линтер и скрипты без браузера.
3. **С браузером, в `make verify`.** e2e на реальном Chrome: всё, что зависит от CDP,
   проверяется только здесь.

## 4. Ограничения по одному

### 4.1. Permissions в `.claude/settings.json`

- **Что запрещено:** `Read(.env*)`, `Read(**/.env*)`, `Bash(git push:*)`,
  `Bash(git commit:*)`, `Bash(rm -rf:*)`.
- **Зачем.** Секреты не попадают в контекст агента. Коммит и пуш — точка, где
  человек подтверждает зелёный `make verify`. `rm -rf` закрыт как необратимое действие.
- **Следствие.** Порядок «тест до кода» нельзя проверить по истории git, поэтому
  автоматика проверяет осмысленность красного, а порядок держится процедурой (ADR-0008).

### 4.2. `depguard` в `make lint` — границы пакетов

- **Где:** `.golangci.yml`, `depguard.rules`.
- **`cdp`** (`internal/cdp/**`): запрещены `internal/command`, `internal/output`, cobra.
  Транспорт переиспользуется всеми командами; знание о CLI или формате вывода
  привязало бы протокол к одной команде и сделало бы его нетестируемым без cobra.
- **`internal`** (`internal/**`): запрещён `cmd`. Зависимость идёт внутрь: точка входа
  собирает команды, а не наоборот.
- **Чего не ловит.** Всё, что не выражается импортом. Для этого есть `guard`.

### 4.3. `make guard` — правила, не выражаемые импортами

Скрипт `scripts/guard.sh`, grep по `internal/` и `cmd/` без тестов.

| Правило | Что ищет | Где разрешено | Зачем |
|---|---|---|---|
| `context.TODO()` | любой вызов | нигде | каждый CDP-вызов получает контекст с таймаутом, иначе команда повиснет на мёртвом порту |
| `panic(` | любой вызов | только вне `internal` | паника даёт стектрейс вместо сообщения и оставляет state недописанным |

### 4.4. `make red RUN=<тест>` — красный осмысленный

Скрипт `scripts/red.sh`. Не входит в `verify`, вызывается на шаге red.

- **Как.** `go test -run <регэксп>` обязан завершиться ненулевым кодом, и в выводе не
  должно быть `build failed`, `setup failed`, `undefined:`, `cannot find package`,
  `no test files`, `no tests to run`.
- **Зачем.** Три ложных красных: тест зелёный до реализации, тест не запустился, тест
  упал от компилятора.
- **Чего не ловит.** Красный от ассерта с неверной причиной — сверяет человек.

### 4.5. `make test-e2e` — поведение на реальном Chrome

- **Как.** `go test -tags e2e ./internal/e2e/...`: headless Chrome, `httptest`-фикстуры,
  каждая команда — отдельный процесс собранного бинаря.
- **Fail-closed.** Нет каталога `internal/e2e` или не найден Chrome — падение, а не
  пропуск.
- **Зачем.** Почти всё поведение CLI — это поведение Chrome. Unit-тесты без браузера
  зелёные и при закрывающихся вкладках, и при сломанном подключении.

### 4.6. `make verify` и `make verify-unit`

`verify` = `lint` + `guard` + `test` + `test-e2e` — единственный признак «готово».
`verify-unit` = то же без `test-e2e`: быстрый цикл, готовность им не подтверждается.

## 5. Что не проверяется автоматически

| Договорённость | Почему нет автоматики | Чем держится |
|---|---|---|
| Тест написан до реализации | коммитит человек, история git не даёт сигнала | скилл `/tdd`, `make red` |
| Диверсия | мутационное тестирование отвергнуто в гейте (ADR-0008) | шаг процедуры |
| Ожидание из плана, а не из кода | тавтологию grep не отличит от честного ожидания | ревью, правило «литералом» |
| Допущение о Chrome проверено спайком | «допущение» машиной не определяется | шаг «Спайк» в плане этапа, раздел в ADR |
| ADR на нетривиальное решение | «нетривиальность» машиной не определяется | `/new-adr`, маркер `// ADR:` |
| Вкладку закрывает только `pages close` | нет статического признака | принцип в `CLAUDE.md`, e2e-проверка числа вкладок |
| Секреты не пишутся в лог и state без маскирования | нет дешёвого статического признака | принцип в `CLAUDE.md`, e2e на `<redacted>` (Э4) |

## 6. Принцип fail-closed

**Гардрейл, который молча ничего не проверил, хуже отсутствующего.** Где это
реализовано:

- `red.sh` считает красный от компилятора отказом, а не успехом.
- `test-e2e` падает, если e2e нет или Chrome не найден.

Проверка, которая при неожиданном входе возвращает «всё хорошо», не принимается.

## 7. Куда добавлять новое ограничение

| Что хочется запретить | Куда | Почему туда |
|---|---|---|
| Импорт пакета из другого пакета | `depguard` в `.golangci.yml` | выражается импортом, проверяется точно |
| Паттерн в коде (вызов, строка) | `scripts/guard.sh` | grep дешёвый, правило и «зачем» лежат рядом |
| Отсутствие артефакта (e2e-кейса) | Go-тест рядом с проверяемым кодом (образец — `cmd/chromectl/commands_coverage_test.go`) или скрипт в `scripts/` | проверка наличия, а не содержания; Go-тест видит структуру (дерево cobra), grep — только текст |
| Поведение с браузером | e2e в `internal/e2e/` | зависит от Chrome, иначе не проверить |
| Действие агента, которое подтверждает человек | `permissions.deny` в `.claude/settings.json` | не выполняется вовсе |

Новое ограничение обязано попасть в `make verify`. Ограничение, которого нет в
`verify`, для процесса не существует.

## 8. Быстрая диагностика срабатываний

| Сообщение | Причина | Что делать |
|---|---|---|
| «транспорт не знает про …» (depguard) | `internal/cdp` импортирует команду, вывод или cobra | передать нужное параметром из команды |
| «internal не зависит от точки входа» | импорт `cmd` из `internal` | перенести общее в `internal` |
| «context.TODO()» | заглушка контекста | передать контекст с таймаутом |
| «panic в internal» | паника в рабочем коде | вернуть ошибку |
| «зелёный до реализации» (`make red`) | тест не задаёт нового поведения или не запустился | проверить имя и ожидание |
| «падение не от ассерта» (`make red`) | код не собирается | сначала заглушка сигнатуры |
| «e2e-тестов ещё нет» | `internal/e2e` отсутствует | до Э1 — ожидаемо; после — написать e2e |
