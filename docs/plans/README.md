# Планы реализации

`docs/plans/` — **комплект планов**, а не одна большая простыня. Крупная задача режется
на этапы, каждый этап — отдельный файл плана, а этот README — реестр: порядок,
зависимости и критерий готовности каждого этапа.

План отвечает на вопрос **«как будем делать»** и живёт до реализации. Спека
(`docs/api/openapi.yaml`, миграции, `DESIGN.md`) отвечает на «что», код — на «как
сделано», ADR (`docs/adr/`) — на «почему именно так». План устаревает и остаётся в
истории; ADR остаётся навсегда.

## Резка — вертикальными срезами

Этап — не слой, а срез через все слои. Каждый этап проходит путь
**миграция → спека → генерация → домен → транспорт → экран на живых данных**, и после
каждого есть что показать. Горизонтальная резка («сначала все миграции, потом весь
домен») запрещена: она даёт готовность 0 % до самого конца.

Один этап — один план. Если внутри этапа оказываются разные зоны ответственности
(например, внешний адаптер и логика очереди), этап разбивается на **дочерние планы**
`etap-N a/b/c`: у каждого свой критерий готовности, родитель остаётся зонтиком в реестре.

Признаки, что этап нарезан правильно:

- его результат можно показать (экран, ручка, прогон end-to-end), а не «код написан»;
- критерий готовности проверяется наблюдением, а не чтением диффа;
- он не тянет за собой половину незапланированного.

## Шлагбаумы — решения, нужные до старта

Вопросы, на которые не может ответить исполнитель. Пока ответа нет, зависимый этап
не начинается — это фиксируется явно, а не всплывает в середине работ.

| Что решить | Кто решает | Блокирует |
|---|---|---|
| Формулировка вопроса с вариантами | владелец задачи | Э4 |

Закрытый шлагбаум не удаляется, а зачёркивается с датой и принятым решением — иначе
через месяц вопрос переоткрывается.

## Решения, зафиксированные для всех планов

Сквозные договорённости, которые иначе пришлось бы повторять в каждом файле: правила
предметной области, выбранные внешние системы, формат сессии и т. п. Нетривиальное
из этого списка дублируется в ADR — здесь только ссылка.

## Правила исполнения любого плана

- **Spec-first**: контракт (`openapi.yaml` / миграция / `DESIGN.md`) правится до кода,
  `gen/` и `front/src/gen/` руками не редактируются.
- **Слои**: правило — в `internal/service/entity`, сценарий — в
  `internal/service/usecase/<операция>`, доступ к данным — в `internal/repository`,
  маппинг и коды ответов — в `internal/httptransport/schemas`.
- **UI — story-first**: токены в `DESIGN.md` → story на моках → визуальная проверка
  скриншотом → подключение к API.
- **Готовность** — зелёный `make verify`. Ничего другого «готовым» не считается.
- **Нетривиальное решение по ходу** — новый ADR и маркер `// ADR:` в коде.
- **Отклонение от плана** — не молчаливое: правится шапка плана («Отклонение от плана»,
  «Правки по ходу»), чтобы файл описывал сделанное, а не задуманное.

## Как завести план

Скопировать `0000-template.md`, назвать `etap-N-kratkiy-zagolovok.md` (транслит,
kebab-case), добавить строку в реестр выше. Процедура — скилл `/new-plan`.

Все планы пишутся на русском.
