# План: слой DTO (доменные сущности) в `internal/dto`

> **Статус: отменён.** Решение пересмотрено: вместо транспортно-независимых структур
> введён доменный слой (`internal/service/entity` + `usecase`), каталога `internal/dto`
> в проекте нет. Действующее решение — `docs/adr/0005-domennyy-sloy-vmesto-dto.md`;
> исходное `docs/adr/0001-dto-kak-vnutrenniy-kontrakt.md` помечено как заменённое.
> План оставлен как история — он объясняет, откуда взялся запрет прямого маппинга
> строк БД в модели HTTP.

## Контекст

Сейчас проект минималистичен: хендлеры маппят строки БД (`gen/db`, sqlc) напрямую
в HTTP-модели (`gen/api`, oapi-codegen). Двух «крайних» типов хватает только пока
доменных сущностей нет (есть лишь health-check). Как только появятся реальные
сущности, прямой маппинг `gen/db` ↔ `gen/api` в хендлерах:

- связывает HTTP-контракт со схемой БД (любая правка таблицы протекает в ответы API);
- размывает место, где живёт «настоящая» модель домена;
- мешает скрывать приватные поля БД (`password_hash` и т.п.) от HTTP-слоя.

Задача — ввести **внутренний контракт домена** в `internal/dto`: единый каталог
канонических доменных сущностей, вокруг которых строится приложение. Это **не**
следствие HTTP-ручки и не привязано к ней — dto одинаково обслуживает любой адаптер:
HTTP (`gen/api`), БД (`gen/db`), сообщения Kafka, значения в Redis/кэше, фоновые
задачи. Каждый адаптер имеет свои «крайние» типы (сгенерированные или сериализуемые),
а `internal/dto` — стабильный центр между ними.

Главная ценность: глядя в `internal/dto`, видно, **какие доменные сущности есть в
системе и зачем** — это самодокументируемый внутренний контракт.

Решения, согласованные с пользователем:
1. Роль `internal/dto` — **внутренний контракт / каталог доменных сущностей**,
   независимый от транспорта. Любой адаптер маппит свои типы ↔ dto: например `store`
   возвращает dto (конвертит `gen/db` → dto), хендлеры маппят dto ↔ `gen/api`,
   будущий consumer Kafka маппит сообщение ↔ dto.
2. Сейчас заводим **только структуру слоя + документацию** (без выдуманной сущности).
   Реальный пример появится при первой настоящей сущности.
3. Зафиксировать концепцию: раздел в `CLAUDE.md` + шаг в скилле `add-endpoint`.

## Принцип слоя (что фиксируем)

`internal/dto` — стабильный центр, к которому сходятся все адаптеры системы:

```
        gen/api (HTTP)  ─┐
        gen/db  (БД)    ─┤
        Kafka-сообщение ─┼──►  internal/dto  ◄── единый внутренний контракт
        Redis/кэш       ─┤        (доменные сущности)
        фоновые задачи  ─┘
```

Поток HTTP-запроса как частный случай (один из адаптеров):

```
HTTP  ──gen/api──►  handler  ──dto──►  store  ──gen/db──►  Postgres
        (req)                  (entity)         (rows)
HTTP  ◄─gen/api──   handler  ◄──dto──   store  ◄─gen/db──   Postgres
        (resp)                 (entity)         (rows)
```

- `internal/dto` хранит **чистые доменные структуры** — без бизнес-логики, без тегов
  сериализации конкретного транспорта, без импортов `gen/api`, `gen/db` и драйверов
  (чтобы домен оставался стабильным центром без циклов и не зависел от адаптеров).
- Маппинг живёт **на стороне адаптера**, а не в dto:
  - **`gen/db` ↔ dto** — в `internal/store` (импортирует `gen/db` и `dto`, отдаёт dto);
  - **dto ↔ `gen/api`** — в `internal/handler` (HTTP-адаптер);
  - будущие адаптеры (Kafka-consumer, Redis-репозиторий) маппят свои типы ↔ dto
    у себя в пакете по той же схеме.
- Узкий интерфейс `Store` (и интерфейсы других адаптеров) объявляются в терминах
  dto-типов — фейк в тестах возвращает dto, как и раньше без БД.

Это не отменяет spec-first и не меняет `Makefile`/кодогенерацию: `internal/dto`
пишется руками, не генерируется и не защищается хуком `protect-gen.sh`.

## Пример описания DTO

Так выглядит описание доменной сущности в `internal/dto` (иллюстрация для `doc.go` и
`CLAUDE.md`; в коде сейчас не заводится — реального домена ещё нет). Один файл на
сущность, `internal/dto/user.go`. Каждое поле снабжается комментарием: что это и
зачем — именно эти описания делают `internal/dto` читаемым каталогом домена.

```go
package dto

import "time"

// User — доменная сущность пользователя: то, чем оперирует приложение
// внутри, независимо от транспорта. Адаптеры (HTTP, БД, Kafka) маппят
// в неё и из неё свои типы.
type User struct {
	ID           int64     // уникальный идентификатор пользователя в системе
	Email        string    // адрес для входа и связи; уникален
	DisplayName  string    // отображаемое имя, показывается в UI
	PasswordHash string    // bcrypt-хеш пароля; только домен и БД, наружу не отдаётся
	CreatedAt    time.Time // момент регистрации (UTC)
}
```

Правила, которые показывает пример:
- **каждое поле описано** комментарием (назначение, ограничения, видимость);
- **чистая структура** — без тегов (`json:`, `db:`), без методов с бизнес-логикой,
  без импортов `gen/api`/`gen/db`/драйверов; разрешена только стандартная библиотека
  (`time` и т.п.);
- **именование по домену**, а не по таблице или по ответу API (`User`, а не `UserRow`
  или `UserResponse`);
- приватные поля (`PasswordHash`) присутствуют в домене — адаптеры сами решают, что
  отдавать наружу.

Маппинг — на стороне адаптера, не в `dto`:

```go
// internal/store: БД-адаптер (gen/db → dto)
func toUser(r db.User) dto.User {
	return dto.User{ID: r.ID, Email: r.Email, DisplayName: r.DisplayName,
		PasswordHash: r.PasswordHash, CreatedAt: r.CreatedAt}
}

// internal/handler: HTTP-адаптер (dto → gen/api, PasswordHash не отдаётся)
func toUserResponse(u dto.User) api.User {
	return api.User{Id: u.ID, Email: u.Email, DisplayName: u.DisplayName}
}
```

Та же `dto.User` затем переиспользуется другими адаптерами (Kafka-сообщение, запись в
Redis) — их маппинг живёт в их пакетах по той же схеме.

## Изменения

### 1. Создать `internal/dto/doc.go`

Новый пакет `dto` с документирующим комментарием пакета (на русском), описывающим:
`internal/dto` как **внутренний контракт / каталог доменных сущностей**,
независимый от транспорта (HTTP, БД, Kafka, Redis, фоновые задачи); правила (чистые
структуры с описанием каждого поля, без бизнес-логики и сериализации конкретного
транспорта, без импорта `gen/*` и драйверов); принцип «маппинг — на стороне адаптера»
(store: `gen/db`↔dto; handler: dto↔`gen/api`; иные адаптеры — по той же схеме). Файл
также не даёт каталогу быть пустым (git не трекает пустые папки) — каталог попадёт в
шаблон через `init.sh`.

Содержит только `// Package dto ...` + `package dto` — компилируется как валидный пустой
пакет. Примеры в комментарии ссылаются на пакеты по коротким именам (`gen/db`, `gen/api`),
без полного module-path → плейсхолдер `github.com/your-org/chrome_skill` в `init.sh` не нужен.

### 2. `CLAUDE.md` — раздел «Архитектура»

В подразделе **Слои** (строки 83–87) после описания `store` добавить абзац про dto:
`internal/dto` — внутренний контракт/каталог доменных сущностей, **независимый от
транспорта** (HTTP, БД, Kafka, Redis, фоновые задачи); по нему видно, какие сущности
есть в системе и зачем. dto — чистые структуры с описанием каждого поля, без
бизнес-логики и без импортов `gen/*`/драйверов; маппинг живёт на стороне адаптера
(`store`: `gen/db`↔dto; `handler`: dto↔`gen/api`; новые адаптеры — аналогично).
Уточнить, что интерфейс `Store` (и интерфейсы других адаптеров) объявляются в терминах
dto-типов.

### 3. `.claude/skills/add-endpoint/SKILL.md`

В шаг 3 (SQL/store, строки 14–16) и шаг 4 (хендлер, строки 17–19) вплести dto
(HTTP — частный случай адаптера, концепция dto от ручки не зависит):
- после генерации `gen/db` — описать/обновить доменную сущность в `internal/dto`
  (единый каталог сущностей, поля с комментариями), метод `store` конвертит
  `gen/db` → dto и возвращает dto;
- хендлер маппит `gen/api` request → параметры store и dto → `gen/api` response;
- интерфейс `Store` расширяется методом, возвращающим dto.

Короткой ремаркой отметить, что та же сущность из `internal/dto` переиспользуется
другими адаптерами (Kafka, Redis, фоновые задачи) — новые типы dto заводятся под
сущность, а не под конкретный эндпоинт.
