# 0009. CLI без демона

- **Статус:** принято
- **Дата:** 2026-09-15
- **Заменяет:** ADR-0002, ADR-0004, ADR-0005, ADR-0006, ADR-0007 (решения шаблона
  HTTP-сервиса, из которого вырос репозиторий)
- **Связано:** план `docs/plans/dapper-tinkering-raccoon.md`, реестр
  `docs/plans/README.md`

## Контекст

Агенту нужно управлять браузером: вкладки, снапшот с uid, ввод, консоль и сеть,
эмуляция, трейс. Постоянный процесс-посредник с коллекторами консоли и сети на каждую
вкладку и картой uid в памяти живёт всю сессию агента и копит память.

Репозиторий был создан из шаблона HTTP-сервиса (echo, Postgres, sqlc, Vue/Storybook).
Ни одна из этих частей задаче не нужна.

## Решение

1. **Резидентный процесс один — сам Chrome.** `chromectl browser start` запускает его
   detached с `--remote-debugging-port` и отдельным `--user-data-dir`,
   `browser stop` закрывает.
2. **Одна команда — одно подключение.** Остальные команды подключаются к порту,
   выполняют одно действие, отсоединяются от вкладки (`Target.detachFromTarget`) и
   завершаются.
3. **Состояние между вызовами — в файле.** `~/.cache/chromectl/<port>/state.json`
   (каталог `0700`, файлы `0600`, поле `version`): pid, выбранная вкладка, карта uid
   `{targetId, frameId, loaderId, backendNodeId}`, настройки эмуляции. Команды меняют
   его через `Store.Update` под `flock` каталога: изменение накатывается на свежий
   state, и параллельные команды на одном порту не затирают друг друга.
4. **Go-бинарь, свой тонкий CDP-клиент** на websocket и типах
   `github.com/chromedp/cdproto`.
5. **Команды** — вкладки и навигация, снапшот и ввод, эмуляция, консоль и сеть,
   трейс, Lighthouse, heap snapshot. Агент пользуется ими через скиллы проекта.
6. Шаблон сервиса удалён целиком. Из него остаются планы-срезы, ADR, тест как
   спецификация (ADR-0008) и гардрейлы `lint`/`guard`/`red`.

## Почему именно так

**Почему не держать свой лёгкий демон.** Любой резидентный процесс, который копит
события по вкладкам, воспроизводит исходную проблему. Chrome уже хранит основное
состояние (вкладки, DOM, буфер консоли), дублировать его в памяти второго процесса
незачем.

**Почему Go, а не Node.** Один бинарь без рантайма, мгновенный старт на каждый вызов,
а инструменты шаблона (`golangci-lint`, `make red`, depguard) сохраняются. Цена — нет
движка insights DevTools и Lighthouse в процессе: insights считаются упрощённо на Go,
Lighthouse запускается через `npx lighthouse --port`.

**Почему не контексты `chromedp`.** У `RemoteAllocator` в `chromedp.NewContext`
принудительно `c.first = false`, и отмена контекста с `WithTargetID` выполняет
`DetachFromTarget` + `CloseTarget`. Каждая команда закрывала бы вкладку, с которой
работает. Проверено по исходнику `chromedp` (master, `chromedp.go`) при ревью плана.

**Почему Bash + curl отвергнут.** Снапшот по фреймам, карта uid и разбор трейса на
Bash получаются хрупкими.

## Последствия

Что теряется без демона и как это закрывается:

| Возможность | Как без резидентного процесса |
|---|---|
| uid снапшота | Карта в state `uid → {вкладка, target, фрейм, loaderId, backendNodeId}`; узел перезагруженного или сменённого документа `DOM.resolveNode` не находит → ошибка «снапшот устарел». Отдельная сверка `loaderId` в Э2 оказалась лишней (диверсия её не заметила) и удалена; `loaderId` остаётся в ключе, по которому узел сохраняет uid между снапшотами |
| Эмуляция | Настройки вкладки — в state, применяются при каждом подключении. Тему, touch, user agent и сеть CDP снимает при отключении сессии: между командами страница живёт без них. Viewport (`setDeviceMetricsOverride`) отключение не снимает — сброшенный viewport `emulate` снимает явно `Emulation.clearDeviceMetricsOverride` (спайк Э3) |
| Консоль | `Runtime.enable` / `Console.enable` повторяют буфер Chrome (спайк, допущение 3) |
| Диалоги | Новая сессия не видит диалог, открытый при прошлой, а страница остаётся заблокированной (спайк, допущение 5 опровергнуто). Поэтому команда, работающая со страницей, следит за диалогами на время работы и закрывает их до выхода: по умолчанию accept и печатает текст диалога. `--dialog accept\|dismiss\|<текст>` — на один вызов, `dialog accept\|dismiss [--text]` — политика для следующей команды, хранится в state. Застрявшую вкладку разблокирует `navigate --reload` (решение владельца задачи 2026-09-15) |
| Сеть | Истории до подключения нет: список из Performance API, детали — только из `--capture` в рамках одной команды; секреты маскируются, тело ≤ 1 МБ |
| `initScript` | Действует в рамках одной команды `navigate` |
| Trace | `start`/`stop` не разделить: запись одной командой `perf trace` |
| Lighthouse | Нужен Node (`npx lighthouse --port`) |

Допущения, которые проверяет спайк Э1 до основной реализации:
1. после выхода команды вкладка остаётся открытой;
2. `backendNodeId` стабилен между сессиями, в том числе в OOPIF;
3. `Console.enable` повторяет сообщения, залогированные до подключения;
4. эмуляция сбрасывается при отключении сессии;
5. `Page.enable` повторно присылает открытый диалог;
6. `Browser.setWindowBounds` работает в `--headless`;
7. `lighthouse --port` подключается к запущенному Chrome и не закрывает его.

Опровергнутое допущение — повод пересмотреть соответствующую строку таблицы выше.
Пересмотреть решение целиком стоит, если Chrome начнёт терять состояние, без которого
CLI не обходится (например, перестанет повторять буфер консоли).

## Результаты спайка

2026-09-15, Chrome 153.0.8010.36 `--headless=new`, macOS. Тест —
`internal/cdp/spike_test.go` (`go test -tags spike ./internal/cdp/ -run TestSpike -v`),
каждое новое websocket-подключение имитирует отдельный вызов CLI, у каждого подтеста
своя вкладка.

| # | Допущение | Итог | Факт |
|---|---|---|---|
| 1 | Вкладка переживает выход команды | **подтверждено** | После `Target.detachFromTarget` и закрытия websocket набор вкладок не меняется; обрыв websocket без detach вкладку тоже не закрывает |
| 2 | `backendNodeId` стабилен между сессиями, в том числе в OOPIF | **подтверждено** | `DOM.resolveNode` по `backendNodeId` из прошлой сессии находит тот же узел без `DOM.getDocument`; для OOPIF — в сессии, подключённой к его `targetId`. OOPIF появляется через `Target.setAutoAttach` как target типа `iframe`; AX-дерево страницы содержит `backendDOMNodeId` своих узлов |
| 3 | Консоль до подключения доступна | **подтверждено** | И `Runtime.enable` (`consoleAPICalled`), и `Console.enable` (`messageAdded`) повторяют сообщения, залогированные до подключения. `Log.enable` для `console.*` записей не отдаёт |
| 4 | Эмуляция сбрасывается при отключении | **подтверждено частично** (уточнено спайком Э3, `TestSpikeOverridesOnDetach`) | Снимаются: `setEmulatedMedia` (тема), `setTouchEmulationEnabled`, `setUserAgentOverride`, `emulateNetworkConditions`. **Не снимается `setDeviceMetricsOverride`**: 390×844 остаётся после отключения сессии. В Э1 проверялась только тема |
| 5 | Открытый диалог виден новой сессии | **опровергнуто** | Диалог, открытый при сессии, которая затем отключилась, блокирует страницу (`Runtime.evaluate` висит), но новая сессия его не видит: `Page.handleJavaScriptDialog` → `-32602 No dialog is showing`, `Page.enable` не отвечает, `javascriptDialogOpening` не повторяется. Разблокирует `Page.reload`; `Target.closeTarget` вкладку закрывает |
| 6 | `Browser.setWindowBounds` работает в headless | **подтверждено** | 800×600 → в новой сессии `outerWidth` = `innerWidth` = 800 |
| 7 | `lighthouse --port` работает с запущенным Chrome | **подтверждено** | `npx lighthouse@12 --port` вернул оценку seo, набор вкладок до и после совпал |

Попутно:
- Chrome не запускается внутри песочницы агента (Seatbelt): не создаётся каталог
  сокета ProcessSingleton и файлы Crashpad. e2e и спайк запускаются вне песочницы.
- `--remote-debugging-port=0` + файл `DevToolsActivePort` в `--user-data-dir` дают
  свободный порт без гонки; первая строка — порт, вторая — путь browser websocket.
  **С явным портом Chrome 153 этот файл не пишет** (выяснено при реализации Ш4 Э1):
  `browser start` проверяет готовность запросом `/json/version` на свой порт, а до
  запуска — что порт свободен, иначе ответил бы чужой процесс.
- Проверка подстроки в сообщениях CDP ведётся ASCII-маркерами: первый прогон с
  кириллическим маркером дал ложный отрицательный результат по консоли.
