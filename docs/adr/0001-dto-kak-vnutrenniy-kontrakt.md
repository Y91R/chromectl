# 0001. DTO как транспортно-независимый внутренний контракт домена

- **Статус:** заменён ADR-0005
- **Дата:** 2026-06-15
- **Связано:** `internal/dto/doc.go`, `internal/store`, `internal/handler`;
  план — `docs/plans/dto-zesty-thacker.md`

## Контекст

Код генерируется с двух сторон: `gen/api` (oapi-codegen из openapi.yaml) и
`gen/db` (sqlc из SQL). Если хендлеры и стор работают напрямую с этими типами,
домен оказывается размазан по сгенерированным структурам, привязан к форме
транспорта и БД, а интерфейс `Store` нельзя описать без импорта `gen/*`.

## Решение

Между `gen/db` и `gen/api` вводится слой `internal/dto` — единый каталог
канонических доменных сущностей. Маппинг живёт на стороне адаптера: `store`
конвертит `gen/db` ↔ dto, `handler` — dto ↔ `gen/api`. Интерфейс `Store`
объявляется в терминах dto-типов.

## Почему именно так

Рассматривали два пути. (1) Работать напрямую с `gen/*` — меньше кода, но домен
жёстко связан с транспортом, а смена формы API/таблицы протекает во все слои.
(2) Полноценный сервис-слой — избыточно для минималистичного шаблона. dto —
середина: стабильный центр без бизнес-логики, который одинаково обслуживает любой
адаптер (HTTP, БД, Kafka, кэш, фоновые задачи) и тестируется фейком без БД.

## Последствия

Плюс: домен не зависит от адаптеров, нет циклов, `Store` мокается тривиально,
новые адаптеры подключаются по той же схеме. Минус: ручной маппинг и дублирование
полей между dto и сгенерированными типами — сознательная плата за развязку.
