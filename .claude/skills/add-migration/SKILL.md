# Новая миграция БД

**Схема едет только вперёд.** Правка уже закоммиченной миграции блокируется хуком:
применённый файл разъезжается с состоянием прода. Несовместимое изменение делается
по expand/contract: сначала добавь новое (колонка nullable/с дефолтом, новая таблица),
при нужде сделай backfill и переключи чтение/запись — это одна миграция. Удаление или
переименование старого — **отдельная** последующая миграция, накатываемая после того,
как код перестал использовать старое; до тех пор запиши его в `docs/adr/DEPRECATIONS.md`.

1. **Создать пару файлов**: `make migrate-create name=<snake_case_имя>` —
   появятся `internal/db/migrations/NNNNNN_<имя>.up.sql` и `.down.sql`.
   Руками файлы миграций не создавать и не переименовывать.
2. **Заполнить обе стороны**: `.up.sql` — изменение схемы, `.down.sql` — честный
   откат. «Откат», который ничего не делает, хуже отсутствующего: он врёт
   `make test-migrations`. DDL пиши идемпотентно там, где это естественно
   (`IF NOT EXISTS` для CREATE).
3. **Применить локально**: `make docker-db` (если БД не поднята), затем
   `make migrate-up`. Полный цикл up → down → up проверяет `make test-migrations`.
4. **Запросы**: SQL к новым таблицам — в `internal/db/queries/*.sql` в формате sqlc
   (`-- name: GetItem :one`). Затем `make generate` — типизированный код появится
   в `gen/db`. sqlc проверяет запросы против DDL миграций, поэтому рассинхрон схемы
   и запроса ловится генерацией, а не в рантайме.
5. **Репозиторий**: `gen/db` оборачивает `internal/repository/<агрегат>/` — наружу
   отдаются **сущности**, а ошибки драйвера переводятся в доменные
   (образец — перевод `23505` в `ErrConflict` в `internal/repository/item`).
   SQL-строк в Go-коде не бывает: это проверяет `make guard`.
6. **ADR (если решение нетривиально)**: неочевидный выбор схемы, денормализации,
   индексов или стратегии миграции — `docs/adr/NNNN-zagolovok.md` (скилл `/new-adr`).
7. **Проверка**: `make verify`, а на живой БД — `make verify-full`.
