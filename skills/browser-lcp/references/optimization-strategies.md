# Оптимизация LCP

## Какие элементы бывают LCP

- `<img>` (у анимированных — первый кадр), `<image>` внутри `<svg>`;
- `<video>` — постер или первый кадр, что раньше;
- элементы с фоновой картинкой через `url()`;
- блочные элементы с текстом.

Не считаются: элементы с `opacity: 0`, покрывающие весь экран (вероятно, фон),
заглушки и малоинформативные картинки. Размер — видимая часть в экране; у картинки —
меньшее из видимого и собственного размера; поля, отступы и рамки не учитываются.

## 1. Убрать задержку загрузки ресурса (<10%)

Самое частое узкое место: ресурс должен начать грузиться сразу.

- **Причины**: картинка подставляется из JS/CSS, `data-src`, `loading="lazy"`.
- Обычный `<img src>` в исходном HTML; **никогда** не lazy-load для LCP-картинки.
- `<link rel="preload" fetchpriority="high">`, если картинку не видно в HTML.
- `fetchpriority="high"` на LCP-`<img>`.
- Ресурс с того же origin или `<link rel="preconnect">`.

## 2. Убрать задержку отрисовки (<10%)

- **Причины**: тяжёлые стили, синхронные скрипты в `<head>`, занятый главный поток.
- Критический CSS встроить, некритичный CSS и JS — отложить.
- Разбить длинные задачи (`chromectl perf insight <trace> LongTasks`).
- SSR, чтобы элемент был в исходном HTML.

## 3. Сократить длительность загрузки ресурса (~40%)

- Современные форматы (AVIF, WebP), адаптивные картинки (`srcset`), сжатие.
- CDN; `Cache-Control`.
- `font-display: swap`, если LCP — текст, ждущий веб-шрифт.

## 4. Сократить TTFB (~40%)

- Меньше редиректов, быстрее ответ сервера.
- Кеш HTML на CDN, вычисления на edge.
- Страница пригодна для bfcache.

## Что говорят разрывы между метриками

- Большой разрыв **TTFB → FCP**: много блокирующих ресурсов или рендеринг на клиенте.
- Большой разрыв **FCP → LCP**: LCP-ресурс недоступен сразу или браузер занят другим.
